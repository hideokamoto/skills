# research-handoff: 調査依頼の受け渡し設計

## 目的

調査結果が読めない・使えないという問題の主因は、分量ではなく、渡し方を依頼の時点で設計していないことにある。

LLM は、相手と共有されている知識や前提を確認せずに、あるものとして話を進める傾向がある。共通の土台を作る発話をほとんど使わない、という報告がある（Shaikh et al., "Grounding Gaps in Language Model Generations", NAACL 2024）。相手の側から「分からない」と伝えるのも、やりとりが続くと減ることがあり、待っていても信号が来るとは限らない。

そのため、主な入口は事後ではなく事前である。

## 入口 A（主）：調査・分析の依頼を受けたとき

### 使う場面

調査・分析・サーベイ・検証を求める依頼で、他のスキルや決まった手順が担当していないもの。

使わない場面

- 別のスキルが担当する調査（記事執筆、顧客データの分析、商談の検討など、その中に調査が含まれているもの）
- 単一の値・一覧・可否だけを求める依頼（「〜の一覧を」「〜は可能か」「〜のバージョンは」）

### 着手前に 3 点を宣言する

質問ではなく宣言にする。宣言して進み、外れていれば相手が止められる状態にするのが目的である。確認を取ることが目的ではないので、返事がなくても進めてよい。

```
判定: この依頼の結論は私が出します（/ 出しません。材料の提示までにします）
前提知識: <分野>は高い、<当該範囲>は薄いものとして書きます
渡し方: <一括 / N 分割 / 先に判定のみ>
```

3 行を超えない。理由の説明は付けない。

### 各項目の決め方

**判定の帰属先。** 結論を自分が出すのは、記事・原稿・スキル・資料・技術的事実の判定など、判断材料が自分の側で揃うもの。出さないのは、顧客・商談・公開可否・社内方針など、判断材料が自分の側にないもの。後者で結論を出すと、根拠のない断定になる。迷う場合は「出します」と宣言して外れを待つ方が、材料の一覧を出すより良い。

**前提知識の仮定。** 分野と当該範囲の 2 層で判定する。

- **分野**: ソフトウェア開発・インフラ・クラウド・開発者向けツールは高い。それ以外の学問領域（認知科学・教育学・言語学・医療・統計手法・法務など）は薄い
- **当該範囲**: 分野が高くても、依頼で名指しされた製品・規格・機能・バージョンがこの会話で初出なら薄い

多くの依頼は「分野は高い、当該範囲は薄い」になる。この場合は、分野側の基礎を説明せず、当該範囲だけを分割して渡す。分野自体が薄い場合は、基礎から順序を作る。

仮定を外すと、失敗の型が変わる。高い相手に説明を足すと冗長になり、薄い相手に細部から入ると理解が成立しない。

**渡し方。** 前提知識が薄い領域では、既定を分割にする。1 応答あたり 1〜2 概念で、部分を先に、全体を後にする。前提知識が高い領域では一括でよい。

### 書くときの規則

- 判定を先頭に置く。網羅の後に判定を置かない
- 留保・限界・未検証点は本文に混ぜず、末尾に分離する
- 同じ結論を複数の節で繰り返さない
- 判定に使っていない証拠を載せない
- 前提知識が薄いと宣言した領域では、用語の初出に日本語の説明を付ける。定訳が不確かなものは、そう明記する

これらは意味の指示なので、守ったかどうかを自分で確認する形になる。そのうち機械で判定できる部分だけを書式にして、次節の検査に回す。

## 成果物の書式（機械検査あり）

意味の指示は、破られても外から見えない。破られたことが読む前に見える形にするため、次の書式を固定する。検査が判定するのは存在・位置・数・完全一致だけで、意味は判定しない。

### 書式

先頭 3 行を次のキーで始める。1 行目から順に、空行を挟まない。

```
受け手: <この成果物を読んで次の行動を取る人>
用途: <その人が何に使うか。記事／登壇／商談／返信／社内共有など 1 つ>
字数上限: <数値のみ>
```

見出しは次の位置を守る。

- 最初の `## ` 見出しを `## 判定` にする
- `## 留保` を最後の本文見出しにする。その後ろに置いてよいのは `## 出典` `## 参考` `## 参照` `## 付録` だけ
- 未確定項目は `## 留保` の中に `- [未確定] <内容> 担当: <誰>` の形で書く。担当を空けない

**受け手と用途が決まらないうちは書き始めない。** 1 行目が書けないなら、書けないことを先に伝える。

**字数上限は書き始める前に決め、以後緩めない。** 書いた後に上限を成果物の長さへ合わせると、検査は必ず通るので何も検査しないことになる。緩めた場合は、成果物の留保にその旨を書く。上限は文字数であり、バイト数ではない。日本語は 1 文字約 3 バイトなので、`wc -c` の値を上限にすると 3 倍緩い制約になる。`python3 -c "import sys; print(len(open(sys.argv[1], encoding='utf-8').read()))" handoff.md` のように、ファイルパスを引数で渡して測る。

**上限を超えたら、判定に使っていない証拠から落とす。** 削った内容を黙って消さず、何を落としたかを 1 行で示す。表現を縮めるより、判定に効いていない節を丸ごと落とす方が、読み手の負担が減る。

### 禁止値リスト

出典が未確定、または転記してはいけないと分かっている数値があるときは、1 行 1 件のテキストファイルに集める。値そのものは成果物に書かず、資料名とページだけを書く。検査がリストと成果物を突き合わせる。

### 検査

成果物を提示する前に、このスキルのディレクトリから見た相対パスで実行する。

```
python3 scripts/check_handoff.py <成果物のパス> [--forbidden <禁止値リスト>]
```

`FAIL` が残っている状態で提示しない（exit 1 で終わる）。

**実行結果をそのまま応答に貼る。** 貼らずに「書式は満たしています」と述べない。走らせていなければ貼るものがないので、走らせていない事実が読み手に見える。

`--forbidden` を省略すると、検査は「未検査」と出力する。未検査であることが応答に残る形にしてから省略する。

### 誤検知が出たときの直し方

検査を賢くしない。**書式を直す。** 検査に意味の判定を足すと、再び意味の指示に戻り、破られても見えない状態に戻る。

### この検査が捕まえないもの

- 判定の妥当性、事実と推測の区別、証拠の取捨
- 受け手にとって本当に有用かどうか
- 検査を走らせなかったこと自体。縛れるのは、走らせていない事実が応答から見えるところまで
- 問いのすり替え。書式検査は形だけを見るので、別の問いに答えた成果物でも、書式が合えば通る

## 入口 B（副）：渡し方への不満が来たとき

### 使う場面

直前の出力に対して、内容の誤りではなく、理解しづらさへの不満が示されたとき。

- 「読みにくい」「冗長」「長い」
- 「つまりどういうこと？」「結局何？」「で？」
- 「わからない」「理解するのに時間がかかる」
- 「いきなり細部」「なんの◯◯ですか」

使わない場面

- 要求の読み違い・頼んでいない作業・否定の指摘。stop-and-align が同じリポジトリにあれば、そちらが担当する。処置が逆向き（実行を止めて認識を示す）なので、統合しない
- 事実の誤りの指摘。通常の修正作業

「で？」のような短い一語が直前の調査成果物に対して来た場合は、ここ（分岐 4）で扱う。それ以外で判断に迷う場合は、実行を止める側（stop-and-align）を選ぶ。

### やること

新しい調査を始めない。分量を削るだけで応えない。下の表で分岐を特定し、同じ内容を別の形で出し直す。特定できないときだけ、どの軸が外れているかを 1 行で尋ねる。

| 分岐 | 判別の手がかり | 処置 |
|---|---|---|
| 1. 長さ | 「長い」「多い」。初回の指摘 | 判定に使っていない証拠と節を落とす。文は割らない |
| 2. 密度 | 短くした後にまだ読みにくいと言われる | 1 文 1 主張に割る。留保を本文から分離する。さらに短くはしない |
| 3. 粒度と順序 | 「いきなり細部」「なんの◯◯ですか」「わからない」。前提知識が薄いと宣言した領域、または薄いのに高いと仮定していた領域 | **全体を再送しない。** 最初の 1 ブロック（1〜2 概念）だけを出し、続けるか判断を待つ。参照先を先に置く。**説明を足す方向に動く**（この分岐だけは減らすのではなく増やす） |
| 4. 判断の帰属先 | 「結局何？」「で？」。網羅はできているが判定がない | 判定を先頭に 1 文。誰が決めるかを明示する。可能性の一覧を出し直さない |

分岐 1 と 2 は連続して起こる。1 に対処すると 2 が顕在化する。分岐 3 は、入口 A の前提知識の仮定が外れたことを意味するので、仮定を更新してから出し直す。

### 避けること

- 長さを削るだけで応えること
- 理解度を確認する設問を出すこと（明確化の質問そのものは問題ない。避けるのは、相手に理解を証明させる形）
- 認識を差し出して保留すること（stop-and-align の処置であり、ここでは逆向きになる）
- 冗長と指摘された応答の中で、原因分析を長く書くこと
- 削った内容を黙って消すこと。何を落としたかを 1 行で示す

## 未検証であること

入口 A の 3 行宣言と入口 B の 4 分岐は、実際の 1 会話から抽出した草案である。分岐が 4 つで足りるか、判別が実際にできるかは検証していない。運用して、外れが出る前提で扱う。

検査スクリプトは、同梱のフィクスチャで動作を確認している。次で再実行できる。

```
python3 scripts/run_fixtures.py
```

`references/fixtures/` に、正例 1 本と負例 5 本（ヘッダ欠落・見出し位置・担当欠落・字数超過・禁止値印字）がある。期待する終了コードと一致しないものが 1 件でもあれば、exit 1 になる。

検証したのは、検査が書式の欠陥を検出し、適合した成果物で誤検知しないことまでである。次は未検証である。

- 書式を守った成果物が、実際に受け手に使われるようになるか。検査は形だけを保証する
- 検査を毎回走らせるか。走らせなかった場合を縛る仕組みはない
- `## 出典` などの後置許可リストが 4 つで足りるか
- Claude Code 以外のエージェント上での動作
